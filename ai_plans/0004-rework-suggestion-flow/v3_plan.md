# Rationale

Make the suggestion engine metadata-first without making it untyped: connectors preserve flexible source data in metadata, a single validation/normalization boundary turns the defined metadata schema into typed engine facts, and explicit C# evidence rules deterministically infer and merge time ranges. The Jira connector must deserialize each Jira endpoint into dedicated response/result types so mappings operate on structured API data rather than ad-hoc JSON property traversal or string parsing.

# Acceptance criteria

- [ ] `ActivitySignal` retains universal transport fields (`ConnectorKey`, `ExternalId`, `DateStarted`, `DateEnded`) and carries all remaining connector facts—including title and URL—in typed metadata values; first-class `Title` and `Link` fields are removed.
- [ ] A shared metadata schema defines strongly typed metadata keys and accessors for activity kind, subject/work-item identity, actor identity, display title, source URL, correlation IDs, and source-specific values.
- [ ] Every connector validates its required metadata before returning a signal; invalid or incomplete connector records are skipped with diagnostic logging rather than reaching the engine as ambiguous input.
- [ ] The engine normalizes metadata once into typed internal facts and applies deterministic C# evidence rules; it does not distribute string-key lookups, JSON deserialization, or connector-specific field names across merge logic.
- [ ] Evidence rules handle explicit worklogs/calls, bounded commits, bounded Jira comments/status/content edits, and context-only Jira planning or administrative changes; only sufficient corroborated evidence or explicit-duration evidence becomes a suggestion.
- [ ] Merge rules deduplicate by connector/external ID, correlate by declared subject/correlation keys, merge compatible nearby intervals, preserve every contributing raw metadata dictionary, and create canonical suggestion metadata using documented conflict resolution.
- [ ] `SuggestionModel` persists canonical metadata and per-source evidence metadata; returned suggestion contracts expose the information required for later comparison and explainability without restoring title/link fields.
- [ ] `GenerateAsync` and `ReloadAsync` return the newly persisted `IReadOnlyList<SuggestionContract>`; result/outcome contracts and their API payloads are removed.
- [ ] Jira search, worklog, issue, comment, and changelog responses are deserialized into endpoint-specific result types using `System.Text.Json` attributes/converters where necessary; `JsonDocument`, `JsonElement` path walking, and manual string/date extraction are not used for normal successful response mapping.
- [ ] Jira response result types cover pagination tokens/offsets, issue identity, fields requested by JQL, worklog author and duration, changelog author/timestamp/items, and typed before/after values; unknown optional data is handled explicitly.
- [ ] Tests cover typed Jira response deserialization, pagination, metadata validation, evidence-rule outputs, merge outcomes, metadata conflict preservation, and the generate/reload return lists.

# Technical details

Introduce `MetadataKey<T>` and a `SignalMetadata` wrapper over a serializable `IReadOnlyDictionary<string, JsonElement>` (or an equivalent JSON-value representation). `SignalMetadata.Set` and `TryGet` serialize/deserialize through a declared key, while `GetRequired` produces a connector-local validation error. Define stable shared keys such as `activity.kind`, `subject.workItem.id`, `actor.id`, `display.title`, `source.url`, and `correlation.keys`; define connector-owned Jira keys under `jira.*`. Values that are compared structurally, such as a status transition, use small records instead of encoded strings. Preserve the original metadata in source evidence; do not flatten competing source facts into one dictionary.

Add a normalizer that accepts only valid `ActivitySignal` instances and produces an internal `NormalizedSignal` containing `ActivityKind`, subject, actor, correlation keys, an explicit range when present, and the original metadata. Implement rule classes behind an `IEvidenceRule` interface. Rules create `CandidateEvidence` with a bounded time range, weight, explicit-duration flag, and whether it can create a suggestion alone. The initial rule set is: worklog/call (explicit, strong); commit (short bounded window); user-authored Jira status transition, comment, or substantive content edit (short bounded, corroborating); and priority, assignee, sprint, parent/epic, resolution, and move (context only). Keep rule thresholds and windows in options; avoid a general-purpose rule engine until policies need to be edited outside code.

Implement deterministic merge stages: deduplicate source events, partition by primary subject/correlation key, sort by interval and stable source identity, merge only when the gap and evidence compatibility rules allow it, then promote a block when it has an explicit-duration contributor or reaches the configured multi-source confidence threshold. Persist a `SuggestionEvidenceModel` (or enrich `SuggestionSourceModel`) containing connector identity, external ID, normalized interval, activity kind, weight, and raw metadata. Build canonical `SuggestionModel.Metadata` from contributors with declared precedence and conflict rules, while retaining all original evidence metadata for future comparisons.

Replace the current Jira `JiraApiClient` response traversal (`JsonDocument`, `JsonElement`, `GetPropertyPath`, and manual `TryGetDate`) with DTOs tailored to each Jira REST response: `JiraSearchResponse`, `JiraSearchIssue`, `JiraIssueFields`, `JiraWorklogResponse`, `JiraWorklog`, `JiraCommentResponse`, `JiraComment`, `JiraBulkChangelogResponse`, `JiraChangelog`, and `JiraChangelogItem`. Use `JsonPropertyName` for Jira field names and small custom converters only for genuinely irregular values such as Atlassian Document Format or polymorphic custom fields. Map DTOs to connector-domain containers, then map those containers to signals; no engine type may depend on a Jira DTO. Use typed pagination fields appropriate to the selected endpoint and ensure cancellation is propagated for every page.

Use a project-scoped, time-bounded JQL search to select candidates; fetch worklogs/comments and bulk changelogs in paginated typed responses. Filter changelog/comment/worklog events by the connected account ID before producing signals. Request only the fields required for correlation and display, then retain typed optional Jira context (project, work type, current status, labels, components, sprint, parent) in `jira.*` metadata. Construct a deterministic external ID from the endpoint event identity (for example changelog ID plus item index) so overlapping fetch windows are safe.

Refactor persistence, mappings, controller, UI contracts, repositories, and tests together: remove title and link fields, replace generation result contracts with returned suggestions, and ensure reloading deletes only resettable data from successfully fetched connectors. Add fixture JSON captured from Jira API documentation or sanitized responses to verify DTO deserialization independently from the HTTP client and to verify each mapping path produces the expected typed metadata.
